# ARM64 WSL2 baseline — 2026-09-01

## Environment

- Architecture: AArch64
- Kernel: Linux 6.18.35.2-microsoft-standard-WSL2
- CPU allocation: 8 virtual CPUs on a Surface Pro 11 host
- C mode: `native-cpu` (`-O3 -march=native -flto`)
- Runtime: system `libluajit-5.1.so.2`
- Timing tool: Hyperfine with shell execution disabled

The WSL virtual CPU model was not exposed. Results below are local evidence, not portable performance claims.

## Runtime

| Workload | LuaJIT/unannotated | Native or hybrid | Relative result |
|---|---:|---:|---:|
| 5M tiny function calls | 5.7 ms ± 0.6 ms | 154.8 ms ± 18.7 ms | LuaJIT 27.29× faster |
| 1M fifteen-term kernel calls | 3.1 ms ± 0.4 ms | 30.0 ms ± 3.0 ms | LuaJIT 9.82× faster |
| Tiny-program startup | 715.0 µs ± 301.2 µs | 484.0 µs ± 219.7 µs | Native 1.48× faster |

Startup measurements had substantial scheduler noise. The broad conclusion is more reliable than the exact ratio: standalone numeric mode has less startup machinery, while hybrid calls are currently much slower than LuaJIT-compiled Lua.

For context only, the unannotated LuaJIT launcher ran the call workload about 20× faster and the arithmetic workload about 35× faster than the installed PUC Lua 5.4 interpreter. That acceleration belongs primarily to LuaJIT, not zlua-aot.

## Build latency

Observed public CLI build times:

| Backend | Mean/observed time |
|---|---:|
| Native numeric | 11.505 s ± 0.377 s |
| Hybrid | 12.364 s ± 0.279 s |
| LuaJIT fallback | 11.59 s observed |

One fallback build peaked at approximately 460,416 KB RSS. The public script recompiles the Zig emitter on every invocation, so improving compiler caching/build organization is an obvious usability opportunity.

## Interpretation

The initial hybrid implementation proves guarded native execution, but its granularity is too fine for speed. Every call exits LuaJIT-optimized execution, checks the Lua stack, converts arguments, calls C, and converts the result. Small scalar kernels cannot amortize that boundary.

The next meaningful performance target is a coarse native kernel containing loops, locals, and control flow so one boundary crossing performs substantial work. Whole-program numeric mode already shows potential deployment value through smaller artifacts, lower startup machinery, and removal of the LuaJIT runtime dependency, but its current subset is too small for throughput-oriented applications.
